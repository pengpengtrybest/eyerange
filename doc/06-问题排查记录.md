# 06 问题排查记录

按出现顺序记录本工程实际踩到的坑与解决方式，便于复现与规避。

## 1. 交叉链接报 OpenCV 传递依赖未定义符号

**现象**：链接 `eye_range` 时报 `undefined reference to png_set_filter@PNG16_0`、
`TIFFSetErrorHandler@LIBTIFF_4.0`、`google::protobuf::...`，但 sysroot 里明明有这些库。

**原因**：GNU ld 默认不使用命令行上共享库的 `DT_NEEDED` 去解析该库自身的未定义符号。

**解决**：`CMakeLists.txt` 增加

```cmake
add_link_options(-Wl,--allow-shlib-undefined)
```

这些符号在板上运行时由系统库提供，因此放行即可。

## 2. sysroot 依赖闭包缺失与 `/lib` vs `/usr/lib` 混用

**现象**：只同步 `libopencv_*.so*` 时缺 libjpeg/libpng/libtiff/protobuf；
后来用 `ldd` 收集依赖闭包，链接仍然报错，发现依赖文件躺在
`build/sysroot/lib/aarch64-linux-gnu`，而链接器只搜 `usr/lib/aarch64-linux-gnu`。

**原因**：板上 `/lib` 是 `/usr/lib` 的符号链接，`ldd` 输出的路径两种都有；
`tar` 按原路径存储后又丢了前导 `/`，落到了别的目录。

**解决**：板端脚本先在 `/tmp/eye_range_sysroot_stage` 里把头文件、CMake 配置、
全部 `.so`（符号链接与真实文件都复制）统一铺到 `usr/lib/aarch64-linux-gnu/`，
再整棵树打包，本机 `tar --strip-components=1` 解包。

## 3. 启动即段错误（Signal 11）

**现象**：流水线一启动就 core dump，日志停在“流水线已启动”。

**定位**：加 `-rdynamic` + `backtrace_symbols_fd` 崩溃处理器，栈顶是
`eye::DistanceFilter::update(...)+0xc8`；反汇编该地址是 `ldrb w2,[x21,x0]`，
即读取 `track_used[i]`，而 `x21`（`track_used` 数据指针）为 0。

**原因**：`update()` 在遍历 `tracks_` 做匹配的同时，会对未匹配的检测执行
`tracks_.push_back(...)`。GCC 7.5 `-O3` 把“轨迹表为空则跳过内层循环”提升成了
函数入口快路径，容器在循环中被改变后该假设失效，导致空指针解引用。

**解决**：匹配阶段使用进入函数时的固定上界 `existing`，本帧新建的轨迹从下一帧
才参与匹配；同时不再在循环里持有 `Track&`。改写后崩溃消失。

> 教训：遍历容器的同时修改它（哪怕只是 `push_back`）风险很高，
> 尤其在交叉编译、编译器版本较老（GCC 7.5）的情况下。

## 4. 测距慢到不可用（770ms/帧）

**现象**：13 个目标时测距只有 1.2–1.9 fps。

**原因**：两个问题叠加。一是 ROI 取“全宽横带”，宽度 1280–1762px，
SGBM 代价 ≈ 宽×高×视差；二是我们自己开 4 个线程调用 SGBM，
而 OpenCV 内部默认又是 8 线程，4×8 超订导致线程互相抢核，比单线程还慢。

**解决**：

- ROI 水平裁剪为 `[box.x - nd, box.x + box.w]`（保留完整视差范围），
  垂直只取目标中心附近 ≤128 行；面积过大再内部降采样；
- `cv::setNumThreads(1)`，并行只由我们的线程池（默认 6 线程）负责；
- 显示用视差图单独走 `display_scale=0.25` + `display_num_disparities=64`，每 N 帧更新一次。

结果：44ms/帧（14 fps），距离数值与优化前一致。

## 5. Qt 界面不响应 SIGTERM

**现象**：`pkill -f bin/eye_range` 之后进程仍在，SSH 启动脚本挂住不返回。

**原因**：信号处理器只置了全局停止标志，无界面模式的主循环会轮询它，
但 Qt 事件循环不会看这个标志。

**解决**：`common/stop_flag.hpp` 暴露停止标志，`MainWindow::on_tick()` 每 33ms 检查一次，
置位则 `QApplication::quit()`；同时把默认窗口行为改成最大化（板上显示器只有 1024x768）。

## 6. 现场相机画面全白、检测不到目标

**现象**：真实相机跑 30fps，但目标数一直是 0。

**定位**：把画面取回并做灰度统计：左目均值 237、标准差 29，相机对着白墙，
画面本身没有可识别的 COCO 目标（同时也几乎没有立体纹理，视差会大面积无效）。

**结论**：不是程序问题，属于测试场景问题；程序侧已用离线双目图片对
（13 个目标）验证了检测与测距链路。现场测试时把相机对准有纹理、有物体的场景即可。

## 7. 标定 RMS 高达 24.5px（角点检测器混用）

**现象**：用 58 对采集图做标定，双目 RMS = 24.50px（应该 < 0.5px），
基线算出 52.95mm 且 T 的 z 分量有 14mm（水平双目不该有这么大的离面分量）。

**定位**：

1. 用 `scripts/board_calib_analyze.py` 逐对检查左右目几何一致性 ——
   dcy（左右目棋盘中心垂直差）+3~8px、dcx 正值且随距离变化、宽度比 0.91~1.06、
   清晰度 90~170，说明**图像对本身没问题**，问题在解算环节。
2. 用 `scripts/board_calib_solve.py` 做逐视角重投影误差分析，看单目误差分布。

**原因**：C++ 解算里的角点检测是「先试 `findChessboardCornersSB`，失败再退回经典
`findChessboardCorners`」的混合策略。两种算法的角点**排序约定不一致**，
于是部分视角与物体点的对应关系被翻转，这些视角成为离群点，把整体 RMS 拉到 20px 量级。

**解决**：

- 标定解算**只用 SB 一种检测器**，检不到的视角直接跳过（取景器实时预览仍可用更快的经典算法）；
- 增加**逐视角误差分析 + 离群剔除**（每轮按 `max(1.0px, 5×中位误差)` 剔除，最多 4 轮）。

修复后同一批数据：左目 0.239px / 右目 0.233px / **双目 0.412px**，基线 65.23mm（T 的 y/z ≈ 0）。
另外用 `board_calib_verify.py` 验证校正后的极线对齐误差平均 0.266px，确认校正参数正确。

## 8. 一运行界面板子就重启（xfwm4 合成器 + EWMH 全屏）

**现象**：`scripts/run_board.sh ui` 一跑，板子在十几秒到一分钟内**硬重启**：
没有关机记录、没有 panic、`pstore` 为空、看门狗未启用、温度只有 50°C 左右。

**定位过程**（每一步都用 `scripts/board_stress_test.sh` 带监控跑，采样写盘 + sync，
所以即使重启也能取到崩溃前的最后几行）：

| 试验 | 配置 | 结果 |
|---|---|---|
| 1 | 降载 + 窗口模式（NPU0/2 线程/1280x480/15fps） | 稳跑 60s |
| 2 | **默认全屏 + 满配** | **约 20s 后重启**（负载仅 1.55、54.5°C） |
| 3 | 满配 + 无界面 | 稳跑 25s（负载 2.9、56°C） |
| 4 | 满配 + 窗口模式 | 稳跑 60s（负载 3.5、59°C） |
| 5 | 无关程序（tkinter）静态全屏窗口 | 稳跑 45s |
| 6 | 关闭 xfwm4 合成器 + 默认全屏 | **稳跑 60s** |
| 7 | 合成器开启 + 无边框铺满（新的默认） | **稳跑 60s** |

关键对比：试验 4 的负载比试验 2 **更高**却不重启，说明**不是功耗/过热**；
试验 5 说明也不是“全屏”本身；试验 6/7 说明问题出在
**xfwm4 合成器 + EWMH 全屏（`_NET_WM_STATE_FULLSCREEN`）** 这条组合上。

**原因**：这块板的 X 服务器没有可用 GL 驱动（`AIGLX error: Calling driver entry point failed`、
运行时报 `libGL: failed to load driver: rockchip`），合成器只能走软件路径。
窗口进入 EWMH 全屏后，合成器会对它做“取消重定向(unredirect)”的整屏重绘，
在持续大画面刷新下触发了显示驱动的致命错误，最终 SoC 复位。

**解决**：

1. 程序默认改成**无边框窗口铺满可用区域**（`ui.borderless: 1`），看起来与全屏一致，
   但不走 EWMH 全屏路径 —— 合成器开着也稳（试验 7）；
2. 真正的 EWMH 全屏仍保留为 `--fullscreen`，但**只有关掉合成器才安全**：
   `./board_display_check.sh fix`（`xfconf-query -c xfwm4 -p /general/use_compositing -s false`）；
3. 界面刷新率默认从 30fps 降到 20fps，视频缩放默认用最近邻
   （`ui.fps` / `ui.smooth_scale`），降低软件渲染开销；
4. 另提供 `--low-power` 预设（NPU 单核 / 2 线程 / 15fps 采集 / 12fps 界面）。

**顺带修掉的两个界面缺陷**：

- `QLabel` 的 `minimumSizeHint` 会跟随 pixmap 长大，形成“窗口越缩越大”的正反馈
  （实测窗口被撑到 1280x960），已改为 `QSizePolicy::Ignored`；
- 无边框窗口若按整屏几何摆放，会被窗口管理器按顶部面板高度下推、底部溢出，
  改为按 `availableGeometry()` 铺满。

**复现/验证命令**：

```bash
scripts/board_stress_test.sh 5 --log-level warn            # 默认配置带监控跑
scripts/board_stress_test.sh 5 --fullscreen                # 真全屏（合成器开着会重启）
scripts/board_stress_test.sh 5 --windowed                  # 窗口模式对照
```

## 9. 界面导致整机重启：继续深挖（结论未闭环，但已排除一批原因）

第 8 节的“关掉合成器/改无边框”只是延后了重启，继续压测后发现
**任何带界面的运行都会在 20 秒~2 分钟内硬重启**，而无界面可以长期稳定。

补充实验数据（每次都用 `board_stress_test.sh` / `board_kiosk_test.sh` 带监控）：

| 试验 | 配置 | 结果 |
|---|---|---|
| 8 | 满配 + **无界面** 260 秒 | **稳定**（采集 29fps / 识别 30fps / 检出 keyboard、person 等 0.49~0.97m） |
| 9 | 满配 + 无边框铺满（合成器开） | 60s 通过，**约 2 分钟后重启** |
| 10 | 满配 + **linuxfb**（完全不用 X） | **约 2 分钟后重启** |
| 11 | 无关程序（tkinter）静态全屏窗口 45s | 稳定 |

被排除的原因：

- **不是应用内存泄漏**：界面进程 RSS 稳定在 265~269MB，MemAvailable 稳定 7.3GB；
- **不是系统内存不足**、**不是过热**（重启前 54~64°C）、**不是 CPU/NPU 过载**
  （重启前负载仅 1.5，而稳定跑过的窗口模式负载 3.5）；
- **不是 X 服务器/合成器专属问题**（linuxfb 同样重启）；
- **不是内核 panic**：`/proc/sys/kernel/panic = 0`，panic 会挂住而不是重启；
  重启前后没有任何内核日志、pstore 为空 → 属于**硬件级复位**（掉电/PMIC 复位）；
- Linux 侧没有启用看门狗（`RuntimeWatchdogSec` 未设置，`/dev/watchdog` 无人持有）。

当前判断（按可能性排序）：

1. **供电瞬时跌落**：界面渲染（Qt 软件缩放 + 显示刷新）产生高频电流尖峰，
   而 5V 输入/线缆余量不足。我用 ADC ch3 采样（0.44mV/LSB）在 2 秒粒度下没看到跌落，
   但掉电往往发生在微秒级，采样太慢抓不到；该通道也未必是 5V 输入分压。
2. **显示通路（VOP/HDMI）在持续刷新下触发致命错误**：这块板的 GL 驱动本身是坏的
   （`AIGLX error`、`libGL: failed to load driver: rockchip`），Xorg 日志里还出现过
   HDMI-1/HDMI-2 状态反复 connected/disconnected；`xrandr` 显示 EDID 尺寸为 0mm，
   说明 HDMI 链路质量可疑。
3. 板卡本身硬件不稳定（更换 PSU / SD 卡 / 显示器线对比验证）。

**下一步建议**（按性价比排序）：

1. **换供电**：用官方 DC 头 5V/4A 以上电源（不要用电脑 USB 口/手机充电头）；
   这是当前第一嫌疑，也是最容易验证的。
2. **接 USB-TTL 串口**（115200）抓控制台：只有串口能看到复位前最后一句话。
   抓到的日志可以直接发给我分析。
3. **换一根 HDMI 线/换显示器**（`xrandr` 的 0mm EDID 很可疑）。
4. 考虑升级内核/显示驱动（当前 6.1.43-rockchip，2024-07）。
5. 现场先用 `./bin/eye_range --low-power` 或 headless 模式（后者已验证可长时间稳定运行）。

## 10. 结论：根因是供电（2026-10-09 更换电源后复测）

用户更换电源后复测，**问题消失**：

| 试验 | 换电源前 | 换电源后 |
|---|---|---|
| 无边框铺满，满配 | 约 2 分钟重启 | **稳定跑满 300 秒**（负载 5.17、67.5°C） |
| 真全屏，满配 | **约 20 秒重启** | **稳定跑满 180 秒**（负载 5.59、66.5°C） |
| 默认配置（真全屏）+ 截图 | — | 窗口 1280x960+0+0，50 秒稳定 |

关键对照：换电源**前**负载只有 1.5、温度 54°C 就重启；换电源**后**负载 5.17、
67.5°C 依然稳定。这说明当时的复位与负载无关，而是**电源在电流瞬态下塌陷**
导致 SoC 复位（这解释了为什么完全没有任何内核日志、`pstore` 为空、
看门狗未启用）。

同时更正第 8 节的一个中途结论：**“关掉 xfwm4 合成器才稳”是假象**——
那只是把崩溃时间从 20 秒延后到约 2 分钟；换电源后合成器开着、真全屏也稳定。

因此程序侧的改动（无边框模式、20fps 界面、最近邻缩放、`--low-power`）
不再是“规避故障”的必需项，但作为降低峰值功耗的手段保留；
**默认显示模式已恢复为用户要求的真全屏**。

现场建议：供电用 5V/4A 以上 DC（不要用电脑 USB 口/手机充电头）；
一旦再出现“无日志硬重启”，先怀疑供电与线缆，再怀疑显示链路（本机 EDID 上报 0mm）。
